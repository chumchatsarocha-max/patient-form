# ระบบลงทะเบียนผู้ป่วยแบบเรียลไทม์ — ฟอร์มผู้ป่วย + หน้าจอเจ้าหน้าที่

ฟอร์มลงทะเบียนผู้ป่วยที่ส่งข้อมูลไปแสดงบนหน้าจอเจ้าหน้าที่ **ขณะที่ผู้ป่วยกำลังพิมพ์** ทีละช่อง ผ่าน WebSocket พร้อมสถานะว่ายังกรอกอยู่หรือหยุดไปแล้ว พัฒนาด้วย Next.js 16 (App Router) และ Supabase Realtime

> **เป็นเดโมเท่านั้น ห้ามกรอกข้อมูลผู้ป่วยจริง**
> ทุกอย่างที่พิมพ์ลงในฟอร์มจะถูกส่งแบบเรียลไทม์ให้ทุกคนที่เปิดหน้าเจ้าหน้าที่เห็นทันที ระบบนี้ไม่มีฐานข้อมูล ไม่มีการเข้ารหัสข้อมูลที่จัดเก็บ และไม่มีชั้นรองรับ HIPAA/PDPA

**เว็บที่ deploy แล้ว:** **https://patient-intake-console.vercel.app**

## ลองใช้ภายในสองนาที

ต้องเปิดสองหน้าต่างวางคู่กัน (หรือใช้มือถือคู่กับโน้ตบุ๊กก็ได้)

1. **หน้าต่าง A — ฝั่งผู้ป่วย:** เปิดหน้าแรก → กด **เริ่มลงทะเบียน** → ระบบสร้าง session ที่ `/patient/<sessionId>` → เริ่มพิมพ์
2. **หน้าต่าง B — ฝั่งเจ้าหน้าที่:** เปิด `/staff` → เข้าสู่ระบบด้วยรหัสเดโมด้านล่าง → session ที่เพิ่งสร้างจะโผล่ในรายการ → กดเปิด
3. ดูหน้าต่าง B อัปเดตตามที่พิมพ์ในหน้าต่าง A ทั้งค่าในแต่ละช่อง ช่องที่กำลังถูกกรอกอยู่ และแถบ activity trace ด้านบน

**รหัสเจ้าหน้าที่สำหรับเดโม:** username `Admin` / password `Admin@12345`
รหัสนี้แสดงไว้บนหน้าเข้าสู่ระบบอยู่แล้ว จะได้ไม่ต้องเปิดหาจากที่อื่น

## ความสามารถ

**ฟีเจอร์หลัก**

- ฟอร์มลงทะเบียนผู้ป่วย 13 ช่อง แบ่งเป็นขั้นตอน ตรวจความถูกต้องด้วย Zod (ใช้ schema ชุดเดียวร่วมกันทุกช่อง)
- ส่งข้อมูลไปแสดงฝั่งเจ้าหน้าที่แบบเรียลไทม์ — ทุกการพิมพ์ถูก throttle ที่ 200 มิลลิวินาที แล้วส่งเป็น event `field:change`
- สถานะของแต่ละ session แบบสด: `connected` → `filling` → `inactive` → `submitted` → `disconnected` คำนวณจาก Supabase Presence ร่วมกับเวลาที่มีความเคลื่อนไหวล่าสุด
- หน้ารวม session ที่เปิดอยู่ทั้งหมดสำหรับเจ้าหน้าที่ พร้อมหน้ารายละเอียดที่แสดงข้อมูลทั้งใบตามที่ผู้ป่วยกรอก
- เจ้าหน้าที่ที่เข้ามาทีหลังจะขอ snapshot ทั้งก้อน (`state:request` → `state:sync`) แทนที่จะเห็นฟอร์มว่างครึ่งใบ

**รายละเอียดเพิ่มเติม**

- **รองรับสองภาษา (ไทย / อังกฤษ)** — ครบทั้งชื่อช่อง ข้อความ error และสถานะ สลับได้ตลอดเวลา ค่าที่เลือกเก็บใน cookie และประมวลผลฝั่งเซิร์ฟเวอร์ จึงไม่มีอาการภาษาผิดวาบขึ้นมาก่อน ส่วนวันที่ในภาษาไทยแสดงเป็นพุทธศักราช แต่ค่าที่เก็บจริงยังเป็น ISO แบบคริสต์ศักราช
- **ActivityTrace** — แถบ monospace ในหน้าเจ้าหน้าที่ที่เต้นตามจังหวะการพิมพ์ของผู้ป่วย ทำให้รู้ว่า session ยังมีชีวิตโดยไม่ต้องจ้องค่าในช่อง และปิดอนิเมชันให้เองเมื่อผู้ใช้ตั้ง `prefers-reduced-motion`
- **ข้อมูลติดต่อไม่ออกไปอยู่ในหน้ารายการ** — หน้ารวม session ใช้ presence channel แยกที่ส่งแค่ชื่อที่แสดงกับสถานะ ส่วนเบอร์โทร อีเมล และที่อยู่ไม่เคยออกจาก channel ของ session นั้น จึงเห็นได้เฉพาะในหน้ารายละเอียด
- **ประตูเข้าสู่ระบบสำหรับเดโม** ที่หน้า `/staff` ตรวจฝั่งเซิร์ฟเวอร์ผ่าน proxy (middleware) — ดูขอบเขตที่มันกันได้จริงในหัวข้อด้านล่าง
- **การเข้าถึง (accessibility) วางไว้ตั้งแต่โครงสร้าง** — ทุก input ผูก `<label>` จริง, error มี `aria-invalid` / `aria-describedby`, focus ring มองเห็นชัด, สถานะสื่อด้วยข้อความไม่ใช่แค่สี, ปุ่มกดขนาดอย่างน้อย 44 พิกเซล
- **รองรับทุกขนาดจอ** — มือถือเป็นคอลัมน์เดียวพร้อมแถบส่งข้อมูลติดขอบล่าง เดสก์ท็อปเป็นแบบแบ่งครึ่งรายการกับรายละเอียด
- ตัวเลือกวันเกิดที่เขียนเองบน React Aria (ชื่อเดือนไทย/อังกฤษ และช่วงปีถูกจำกัดที่ 120 ปีเท่ากับที่ validation ยอมรับ)
- จัดการการเชื่อมต่อหลุด — channel ต่อใหม่อัตโนมัติเมื่อล้มเหลว และการที่ presence หายไปจะมีช่วงผ่อนผันก่อนจะประกาศว่า session นั้นตัดการเชื่อมต่อแล้ว

## เทคโนโลยีที่ใช้

| ส่วน | สิ่งที่เลือกใช้ |
| --- | --- |
| Framework | Next.js 16.3 (App Router, Turbopack) + TypeScript |
| Styling | Tailwind CSS v4 (กำหนด token ด้วย `@theme` ใน CSS) |
| ฟอร์ม | react-hook-form + Zod v4 |
| Realtime | Supabase Realtime — Broadcast + Presence (WebSocket) |
| ตรวจเบอร์โทร | libphonenumber-js |
| ส่วนประกอบด้าน accessibility | React Aria Components |
| Hosting | Vercel |

**ทำไมถึงใช้ Supabase Realtime แทนการเขียน WebSocket server เอง:** บน Vercel การเชื่อมต่อ WebSocket จะถูกผูกไว้กับ function instance ตัวที่รับ upgrade เท่านั้น ผู้ป่วยกับเจ้าหน้าที่อยู่คนละเบราว์เซอร์และไปตกคนละ instance ดังนั้นต่อให้เขียน WS server เองไว้ใน deployment เดียวกันก็ยัง broadcast ข้ามกันไม่ได้อยู่ดีถ้าไม่มีตัวกลาง อีกทั้ง Supabase มี Presence API มาให้ ซึ่งตรงกับข้อกำหนดเรื่องสถานะ active / inactive พอดี ไม่ต้องประดิษฐ์ heartbeat เอง

โค้ดที่แตะ realtime ถูกจำกัดไว้ใน `src/lib/realtime/` และ `src/hooks/` เท่านั้น ไม่มี component ไหน import `supabase-js` ตรง ๆ ถ้าจะเปลี่ยนผู้ให้บริการจึงแก้แค่สองที่นี้

## เริ่มใช้งาน

**สิ่งที่ต้องมี:** Node.js 20 ขึ้นไป และโปรเจกต์ Supabase (แพ็กเกจฟรีเพียงพอ)

```bash
git clone https://github.com/chumchatsarocha-max/patient-form.git
cd patient-form
npm install
cp .env.example .env.local   # แล้วเติมค่า Supabase สองตัว
npm run dev
```

เปิด http://localhost:3000

### การตั้งค่า Supabase

**ไม่ต้องสร้างตาราง ไม่ต้องทำ migration ไม่ต้องตั้ง row-level security** เพราะระบบนี้ใช้แค่ Realtime Broadcast และ Presence ไม่เคยอ่านหรือเขียนฐานข้อมูลเลย แค่สร้างโปรเจกต์แล้วคัดลอกสองค่านี้จาก **Project Settings → API**

| ตัวแปร | จำเป็น | หมายเหตุ |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | ✅ | `https://<project-ref>.supabase.co` |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | ✅ | publishable key (`sb_publishable_…`) หรือ anon key แบบเดิม **ห้ามใช้ `service_role` key เด็ดขาด** เพราะค่านี้ถูกฝังลงใน bundle ฝั่ง client |
| `STAFF_USERNAME` | ❌ | ไม่ตั้งจะใช้ค่า `Admin` อยู่ฝั่งเซิร์ฟเวอร์เท่านั้น |
| `STAFF_PASSWORD` | ❌ | ไม่ตั้งจะใช้ค่า `Admin@12345` อยู่ฝั่งเซิร์ฟเวอร์เท่านั้น |

`.env.local` ถูก gitignore ไว้ ส่วน `.env.example` มีไว้บอกว่าต้องใส่อะไรบ้าง

## กลไกเบื้องหลังส่วนเรียลไทม์

ใช้สอง channel

- `intake:{sessionId}` — หนึ่ง session ต่อหนึ่ง channel ฝั่งผู้ป่วยเข้าด้วย presence key `patient` ฝั่งเจ้าหน้าที่ใช้ `staff`
- `intake:lobby` — ใช้แค่ presence แต่ละ session ที่เปิดอยู่จะ track ข้อมูลตัวเองไว้ เพื่อให้หน้ารวมของเจ้าหน้าที่รู้ว่ามี session ไหนอยู่บ้าง ข้อมูลใน lobby ไม่มีเบอร์โทรและอีเมล ปิดแท็บเมื่อไหร่รายการก็หายไป และไม่มีการเก็บประวัติย้อนหลัง

สัญญาของ event (ไฟล์ `src/lib/realtime/events.ts` เป็นแหล่งความจริงเพียงที่เดียว)

| Event | ทิศทาง | ข้อมูลที่ส่ง |
| --- | --- | --- |
| `field:change` | ผู้ป่วย → เจ้าหน้าที่ | `{ field, value, at }` |
| `form:submit` | ผู้ป่วย → เจ้าหน้าที่ | `{ at }` |
| `form:reset` | ผู้ป่วย → เจ้าหน้าที่ | `{ at }` |
| `state:request` | เจ้าหน้าที่ → ผู้ป่วย | `{}` |
| `state:sync` | ผู้ป่วย → เจ้าหน้าที่ | `{ data, status, at }` |

เรื่องลำดับข้อความจัดการด้วยหลัก last-write-wins แยกรายช่อง โดยเทียบจาก timestamp `at` — ถ้าข้อความที่เข้ามาเก่ากว่าค่าที่ถืออยู่จะถูกทิ้ง ข้อความที่มาสลับลำดับจึงไม่สามารถทำให้ข้อความเก่ากลับมาทับของใหม่ได้

ค่าคงที่เรื่องเวลาทั้งหมดอยู่ใน `src/lib/constants.ts` ที่เดียว ไม่มีที่อื่น

| ค่าคงที่ | ค่า | ใช้ทำอะไร |
| --- | --- | --- |
| `BROADCAST_THROTTLE_MS` | 200 ms | throttle แบบ trailing ของ `field:change` (พิมพ์รัวสุดได้ประมาณ 5 ข้อความต่อวินาทีต่อหนึ่งช่อง) |
| `ACTIVE_WINDOW_MS` | 3 วินาที | ยังนับว่า "กำลังกรอก" |
| `INACTIVE_AFTER_MS` | 30 วินาที | เปลี่ยนเป็นสถานะไม่เคลื่อนไหว |
| `PRESENCE_TICK_MS` | 5 วินาที | จังหวะ heartbeat ของ presence |
| `DISCONNECT_GRACE_MS` | 5 นาที | presence หลุดบ่อยกว่าการปิดแท็บจริง จึงต้องรอก่อนตัดสิน |

## ข้อตัดสินใจที่อาจถูกตั้งคำถาม

- **อีเมลกำหนดให้เป็นช่องบังคับ** ข้อกำหนดตั้งต้นเขียนไว้ว่า "valid phone number, email if applicable" ซึ่งกำกวม การตีความว่าบังคับเป็นการตัดสินใจ ไม่ใช่การมองข้าม
- **การตรวจเบอร์โทรครอบคลุมรูปแบบเบอร์ไทยและ E.164** (`+<รหัสประเทศ>…`) ผ่าน libphonenumber-js เบอร์ที่ไม่มี `+` จะถือว่าเป็นเบอร์ไทย ไม่ใช่ตัวตรวจที่รองรับรูปแบบภายในประเทศของทุกประเทศ
- **ประตูเข้าสู่ระบบกันหน้าเว็บ ไม่ได้กันข้อมูล** มันคือการตรวจ cookie ใน `src/proxy.ts` เทียบกับ username และ password แค่พอให้ `/staff` ไม่ใช่ลิงก์เปิดโล่ง แต่**ไม่ได้ป้องกันเนื้อหาใน session** เพราะ Realtime channel ยังเป็น public ใครถือ publishable key ก็ subscribe อ่านสิ่งที่ broadcast อยู่ได้ ถ้าจะกันจริงต้องใช้ Supabase Auth ร่วมกับ channel authorization ซึ่งเกินขอบเขตของเดโมที่ไม่มีข้อมูลจริงอยู่ในระบบ
- **ไม่เก็บข้อมูลลงที่ใดเลยโดยตั้งใจ** รีเฟรชหน้าเจ้าหน้าที่กลางคันได้ไม่มีปัญหา (ระบบจะขอ snapshot ใหม่) แต่เมื่อปิดแท็บของ session นั้นหมดทุกฝั่ง ข้อมูลก็หายไปเลย
- **session id เป็น UUID แต่แสดงเป็นรหัสสั้น** ผู้ป่วยจะเห็นรหัส 4 ตัวอักษรที่คำนวณจาก id ด้วย hash แบบคงที่ อ่านออกเสียงที่เคาน์เตอร์ได้ และไม่เรียงตามลำดับจึงไม่บอกใบ้ว่ามีคนมาก่อนหน้ากี่คน

## สิ่งที่ไม่ได้ทำ

ไม่มีระบบ authentication หรือ authorization จริงนอกจากประตูเดโม ไม่มีฐานข้อมูล ไม่มี audit log ไม่มีการเข้ารหัสรายช่อง ไม่มีชั้นรองรับ compliance และไม่มีการทดสอบอัตโนมัติ
